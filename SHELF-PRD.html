Shelf

Product requirements, v1 · 27 August 2026 · Lighthouse 27 LLC

One line

Shelf is where an agency parks every tool it built for a client, on one link the client can actually use.

A standalone product, not an in-house tool.

1. Why this exists

People who cannot write code now ship real software, and 63% of vibe coding users are non-developers. The tools land on Pages, Lovable, Replit, v0. Then they scatter. Six weeks later nobody can find the URL, nobody remembers the prompt that built it, and nobody knows whether the thing is still up.

This hurts agencies more than it hurts owners, because an agency has the volume. An owner has four tools and a bookmark folder. An agency has forty across nine clients, and every one of them is a thing it has to remember, prove it delivered, and hand over cleanly.

So Shelf is sold to the agency and used by the client. The agency gets recall and a handoff artifact. The client gets one link that always works.

The renewal argument, which is the real sale

A live page showing every tool you built for a client, with status and version notes, is the most efficient reminder of value delivered that an agency can own. It is worth $29 a month at renewal time on its own, before anyone talks about convenience.

3. Non-goals

In v1

  • Auth and accounts
  • Multiple shelves per account
  • Tool cards with screenshots
  • Private, unlisted, password, public
  • Client branding per shelf
  • Prompt pocket and version notes
  • Live check and staleness
  • Soft plan caps with a banner

Not in v1, and mostly not ever

  • Any kind of app generator
  • Hosting other people's runtimes
  • Git, diffs, CI, code storage
  • Likes, comments, feeds, remix
  • Team seats and roles
  • Custom domains (column reserved)
  • Stripe billing (v1.5, gated on the kill test)
  • View analytics (v1.5, see 7.4)

The one that matters

Do not pivot into an app builder. Half the AI app builders launched in 2025 were dead by April 2026. Shelf survives by being the thing that outlives them, and it only does that if it never competes with them.

4. Jobs to be done

  1. Park it. Friday, tool is live. Title, one sentence, URL, screenshot, prompt. Thirty seconds, no ceremony.
  2. Find it Monday. Which link is the real one, what did I prompt, is it still up.
  3. Hand it over. Send one link. Client sees only their tools, branded to them, with no trace of anyone else's work.
  4. Ship v2 without losing v1. Swap the URL, write eight words about what changed, and be able to go back.
  5. Prove it is still true. A card that has not been confirmed in 90 days says so, out loud.

If any step requires git knowledge, the product failed. The UI never says branch, commit, repo, pull, merge, diff, or README.

5. Product model

This is the significant change from the original handoff. The unit is not "a user and their shelf." It is an account holding many shelves, one per client.

account (= one user in v1, seats come later)
  └── shelf                one per client. Own slug, branding, visibility.
        └── section        optional. A project inside the client. Free text.
              └── tool     title, sentence, live URL, screenshot, prompt, status
                    └── version   a frozen previous URL + prompt + note

A client with several projects

This is the normal case, not the edge case. One client can easily carry a marketing site, a customer-facing app, and a back office, and each of those has its own two to six tools. A flat grid of twenty cards under one client name is unreadable by about card twelve.

So a tool carries an optional free-text section. The client shelf renders one heading and one shelf rule per section, in the order the sections first appear. A tool with no section sits in an unnamed first group, so a small shelf looks exactly as it does today and nobody is forced to think about grouping until they have enough tools to need it.

Sections are deliberately free text rather than a table. There is nothing to manage, no CRUD screen, no ordering UI: you type "Back office" into the drawer and the section exists. Sections order by the lowest sort_order among their tools, so reordering cards reorders sections for free.

Why this and not a shelf per project

The alternative is letting one client own several shelves, which needs a client entity above shelves and a navigation level under it. It also breaks the thing the product is for: the client would get three links instead of one, which is the scattering problem Shelf exists to end. One client, one link, sections inside it.

Deliberately not built

No separate clients table and no sections table. A shelf is a client, a section is a string. Both would add a join and a management screen and buy nothing in v1. No teams, no roles, no seats: one account is one login. Revisit only if a paying customer asks.

Visibility, which is the whole handoff feature

ModeBehaviour
privateDefault. Owner only. Any stranger hitting the URL gets a 404 with "This shelf is closed." Never a 403, which confirms the shelf exists.
unlistedReachable by link, noindex, not listed anywhere. The normal client mode.
passwordUnlisted plus a passphrase. For client work that is genuinely confidential. In v1 because agencies need it, not v1.5.
publicIndexed, listed on the owner's public profile. For portfolio use.

A tool cannot be more visible than its shelf. Clamp on write, do not validate in the UI only.

6. Screens

Marketing /

One hook, one screenshot of a real client shelf, one CTA. Hook: Every tool you built them. One link. Do not use "GitHub for people who will never type git" anywhere. It sells to developers, who will not pay for this.

Login /login

One card, one field, magic link. "Sign in to your shelf." No password, no OAuth, no social buttons.

Shelves list /app

The home screen. A row per client shelf: client name, tool count, visibility pill, last activity, live/down/stale roll-up. Primary action: New shelf. Empty state headline: One shelf per client. Start with one.

Shelf detail /app/:shelf

The tool grid. Shelf title and blurb inline-editable, visibility control, Copy client link as a prominent button not a menu item, and Add a tool. Cards reorder by drag with up/down as fallback. Empty state: You shipped it. Park it here.

Add tool drawer

Fields in this exact order. Order is the spec, do not rearrange.

  1. Title
  2. One sentence
  3. Live URL
  4. Screenshot drop zone
  5. Section (free text, autocompletes from sections already on this shelf)
  6. Tag chips
  7. Visibility (inherits shelf, private default)
  8. Prompt pocket (textarea, optional)
  9. Builder chip and builder URL (optional)

Primary button: Put it on the shelf. No draft state. Save creates the card. Only title and live URL are required.

Client shelf /s/:slug

What the client sees. Client logo and accent if set, shelf title, blurb, then the grid. If any tool has a section, the grid breaks into one titled run of cards per section, each on its own shelf rule. No Shelf chrome beyond a small footer badge on the free plan. No login prompt. No settings. Nothing that reveals other clients exist.

Tool detail /s/:slug/:tool

Large screenshot, title, sentence, Open tool, tag, latest version note, status. Owner sees three extra blocks the client never does: prompt pocket, version list with Make this live, and the builder link.

404

"This shelf is closed." Nothing else. No search box, no home link that leaks branding.

7. Data model

Changes from the handoff schema are called out below the SQL. TEXT ulid ids, INTEGER epoch ms timestamps.

1. Slug is globally unique

The original was UNIQUE(user_id, slug) while the public route was /s/:slug with no user in the path. Two accounts both slugged maria-bakery and the route cannot resolve. Global uniqueness keeps client links short, which matters because the client pastes them into email.

2. confirmed_at

A green dot proving a URL returns 200 does not prove the tool is still real or in use. The failure this prevents is a card reading LIVE months after the thing behind it died. Every card carries the date a human last said it was true. Past 90 days the card shows a quiet Needs confirming, and a Still true action re-dates it without inventing an edit. Changing the URL, status, or prompt re-dates it automatically.

3. Foreign keys with cascade

The original declared none, so deleting a shelf orphaned everything under it. D1 enforces FKs per session. Since v1 has real delete routes (the original had none at all), this is required, not tidy.

4. views table dropped from v1

It was a D1 write per public page view, on the one table with unbounded traffic, to produce the least valuable number in the product. Ships in v1.5 as a KV counter flushed on a schedule, if anyone asks for it.

5. section is free text, tag stays an enum

They are different axes and both are useful. section answers "which project of theirs is this part of" and has to be whatever the client calls it. tag answers "what kind of tool is this" and stays a closed list so the filter chips remain a fixed, predictable set. Neither replaces the other.

Enums

plan: free, studio. visibility: private, unlisted, password, public. tag: invoicing, booking, inventory, internal, other. status: live, down, draft. builder: pages, lovable, replit, v0, bolt, claude, other.

KV and R2

KV   session:{token}        30 day TTL
     magic:{token}          15 minute TTL, single use
     rate:{ip}:{action}     signup, magic link, ping
     shelfpw:{shelf_id}:{token}   client passphrase session

R2   shots/{user_id}/{tool_id}.{ext}          current screenshot
     shots/{user_id}/{tool_id}/v{n}.{ext}     frozen at snapshot
     logos/{user_id}/{shelf_id}.{ext}

Store as uploaded, key on the real extension. The original keyed everything .webp while specifying png/jpg passthrough, and nothing transcoded.

Three guards that are part of the spec, not hardening later

Ownership. Every route taking an :id resolves it through the session user's account before doing anything. "Session required" is not the check. A test asserts that user A gets a 404, not a 403, on user B's tool.

Live-check is an outbound fetch proxy. Allow http and https only. Reject localhost, private ranges, and cloud metadata endpoints by resolved host. Cap redirects at 3, timeout 5s, treat 200 to 399 as live. Rate limit the owner-triggered ping.

No leakage. Public responses never include prompt, builder_url, email, or any other shelf's existence. Serialise public payloads through an explicit allowlist, never by deleting keys from the internal object.

Why not Cloudflare Access / Zero Trust

Fair question, since Access does email one-time-PIN login for free and costs nothing at small scale. It is the right tool for an internal route and the wrong tool here, for four reasons that all point the same way.

1. The pricing is per seat, and it is charged on signups, not on customers. Zero Trust is free to 50 users, then $7 per user per month. Shelf charges $29. A free-tier signup who never pays would cost $7 a month to exist, and a paying Studio customer would hand a quarter of their revenue to the auth layer. You would also hit the free ceiling at 50 signups, which means the failure arrives exactly when the product starts working.

2. Access authorises a list you configure, it does not let strangers sign themselves up. Policies match on emails, domains, or IdP groups that an account admin sets. Self-serve signup means calling the Cloudflare API to mutate an Access group on every registration, which puts your user directory in Cloudflare's policy engine instead of your own D1.

3. It gates at the perimeter, and Shelf is half public by design. Access sits in front of a hostname or path before your code runs. Shelf serves /s/:slug to anonymous clients and /app to owners from the same origin. Splitting those across hostnames to satisfy the auth layer is the tail wagging the dog.

4. The client never signs in at all. The handoff link has to work for someone with no identity, and the passphrase gate is our own logic over a shelf row. Access cannot express "unlisted link plus a shared word" without provisioning a person.

Where Access does belong: put it in front of Shelf's own internal operator route, the one where you look at signups and caps. That is a fixed list of one person, which is precisely what Access is for.

On SendGrid specifically

Chosen because it is provisioned, paid for at 50k a month, and has sending history. Use a separate API key and its own sending subdomain, never one shared with another product, so a deliverability problem here cannot spread anywhere else. Cloudflare Email Service is the viable alternative now that you can onboard a sending domain, and it would keep everything on one platform. Either is fine. Do not spend a session on it.

Deploy split, the one that already bit you

Workers-with-assets is chosen partly so there is no split. Frontend and API deploy together from one command. Do not later carve the API into a separate Worker for tidiness. The moment they deploy separately, one ships from a branch and the other from a working tree, and production breaks in a way that takes a session to find.

10. Visual system

Direction: paper and shop window. A shelf is a physical object. Cards are things sitting on it, screenshots are the goods in the window. Warm, printed, slightly old-fashioned. It should look like a well-made catalogue, not a dashboard.

Rust is the only primary action colour. Moss means live. Amber means needs confirming. Muted grey means down, because a dead tool should feel absent rather than alarming. There is no blue anywhere in this product.

The accent constraint, which drives everything else

A client shelf can carry the client's accent colour. That means the chrome has to stay neutral enough that an arbitrary hex dropped into it does not collapse the design. Rust is Shelf's brand and appears in the app. On /s/:slug the client accent replaces rust and nothing else changes. Never put two saturated colours next to each other, because one of them will be a stranger's.

Form

  • Radius 3px. Almost square. Paper does not have rounded corners.
  • Borders, not shadows. One hairline in --line. At most one soft shadow in the whole product, on the drawer.
  • The shelf edge. Each row of cards sits on a 2px ink rule that runs the full grid width, with a 1px lighter rule 3px below it. This is the one distinctive device in the design and it is what stops the grid reading as generic cards. Use it on the client shelf and the owner grid, not in the drawer. A section heading sits above its own run of shelves, set in Fraunces small caps against the rule, so a client with three projects reads as three shelf units on one wall.
  • Screenshot is the hero. 16:10, full bleed to the card edges, no padding, no inner border. If there is no screenshot, show a paper-textured placeholder with the tag name set in Fraunces, never a grey box with an icon.
  • Spacing scale 4 / 8 / 12 / 16 / 24 / 32 / 56.

12. Validation

Automated, these are the tests that must exist

  1. Private shelf returns 404 to a logged-out request
  2. Owner can load their own private shelf
  3. User A gets 404, not 403, on user B's tool for GET, PATCH and DELETE
  4. Creating a tool with no title or no live_url fails
  5. Public payload contains no prompt, builder_url, or email
  6. A tool cannot be public under a private shelf
  7. Reorder persists
  8. Changing live_url creates a snapshot holding the previous URL
  9. Make-live writes the snapshot URL onto the tool
  10. Live check rejects localhost, a private IP, and a non-http scheme
  11. Deleting a shelf removes its tools and snapshots
  12. A magic link token cannot be used twice

Manual click script

  1. Sign in, create shelf "Maria's Bakery"
  2. Add Flour run log with a prompt, upload a screenshot
  3. Set shelf to unlisted, copy the client link, open it in a private window
  4. Confirm no other shelf is discoverable from it
  5. Change the live URL with note "v2 vendor names"
  6. Version list shows v1 and v2, make v1 live again
  7. Set a passphrase, confirm the unlock gate
  8. Log out, confirm /app is unreachable
  9. Unknown slug returns the closed copy

Kill test, run after it has been used on two real clients for three weeks

Pass: a client link gets sent to an actual client without prompting, twice. A second shelf is created without coaching. A prompt pocket is read in a later session, by someone trying to find something.

Fail: one vanity shelf and a bounce. Nobody sends a link. Every feature request is a version of "can it build the app". If it fails, do not build Stripe.

14. Open decisions

  1. Name. "Shelf" is a good working name and a hard domain. Decide before the marketing page, not after.
  2. Public profile. Section 5 allows a public shelf but there is no /@handle page in v1. Probably correct. Revisit if the secondary persona shows up.
  3. Screenshot capture. Upload only in v1, as specified. Auto-capture is the single most requested thing this product will get asked for. It is a v2 conversation, and it is a real cost centre.
